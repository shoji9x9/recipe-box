# セキュリティ

- コミットと CI で、gitleaks が秘密情報の混入を調べる。GitHub の secret scanning と push protection も有効にしている。
- 依存の更新と脆弱性の通知は Dependabot が担う。Rust の依存は cargo-deny でも調べる。
- workflow は、job ごとに最小の権限だけを与え、actionlint・ghalint・zizmor・CodeQL で調べる。
- 脆弱性の報告の仕方は [SECURITY.md](../SECURITY.md) にある。

## 費用の対策

ログインの無い公開アプリなので、誰でも API を呼べる。自動化した攻撃で、ワークスペースと IP アドレスを使い分けながらデータを作られても、費用が決まった上限を超えないようにする。

上限は 3 つの層で設ける。下の層ほど、攻撃者が回避できない。

| 層 | 上限 | 超えたとき | 回避の手段 |
| --- | --- | --- | --- |
| IP アドレスごと（Rate Limiting、おおよそ） | ワークスペースを作る: 60 秒に 10 回。書き込む API（レシピの登録・更新・削除、写真の追加・削除、ワークスペースの削除）と画面の書き込み: 60 秒に 30 回 | `429` | IP アドレスを変える |
| ワークスペースごと | レシピ: 80 件。本文: 128 KiB。料理名 100・材料 2,000・手順 5,000 文字。写真: 1 枚 4,000,000 バイト・1 レシピ 5 枚・合計 100,000,000 バイト | `409`・`413`・`400` | ワークスペースを作り直す |
| **アプリ全体**（D1 で数えて厳密に判定） | ワークスペース: 100 個。作る数: UTC の 1 日に 20 個。写真: 合計 5,000,000,000 バイト・追加 UTC の 1 日に 200 回 | `503` | **回避できない** |

- レシピは 1 件で最大およそ 29 KB（7,200 文字をすべて 4 バイトの文字で書いた場合）なので、D1 に入るレシピは最大でも 100 × 80 × 29 KB ≒ 230 MB で、1 つの D1 の上限（無料のプランで 500 MB）の半分に収まる。
  ワークスペースの数の上限（100 個）は、実際に使われると見込む数（50 個ほど）の 2 倍にしている。レシピの数の上限（80 件）は、デモに 1 ページ 20 件で 3 ページ以上のサンプルを入れられる数にしている。
- アプリ全体の上限に達すると、攻撃者だけでなく全員が新しくワークスペースを作れなくなる。費用が際限なく増えるより良いとし、受け入れる。使われなくなったワークスペースは 14 日で自動で消える（docs/spec.md）ので、そのあとはまた作れる。
- 写真（R2）は、無料の範囲を超えると課金されるので、R2 に書き込む前に D1 で上限を判定する。
  - 保存量: 合計 5,000,000,000 バイト（5 GB）は、無料の範囲（10 GB-月）の半分である。ワークスペースが 50 個ほど写真を使っても（50 × 100,000,000 バイト）収まる。
  - 書き込みの操作（Class A）: 写真の追加は 1 日 200 回なので、月に最大 6,200 回で、無料の範囲（100 万回/月）より十分に小さい。
    写真を消しても回数は戻らない（`photo_uploads` に記録を残す）ので、追加と削除を繰り返しても増えない。一覧（ListObjects、Class A）は使わない。削除は無料である。
  - 読み取りの操作（Class B）: 写真のデータの読み取り 1 回が、Worker のリクエスト 1 回になる。無料のプランの Worker は 1 日 10 万リクエストで止まるので、月に最大 310 万回で、無料の範囲（1,000 万回/月）に収まる。
    写真には `Cache-Control: private, max-age=86400` を付け、同じ写真を同じブラウザで 1 日は読み直させない。有料のプランでは Worker が止まらないので、この見積もりは成り立たない。
  - 写真を追加するたびに、アプリ全体の合計を求めるため `photos` の全体を D1 で読む（最大でおよそ 4 万行）。読む行の少ない条件（レシピの枚数・1 日の回数・ワークスペースの合計）を SQL の前に並べ、それを通った試行だけが全体を読むようにしている（SQL は評価の順を保証しないが、SQLite は左から評価する）。
    全体の合計が上限に達した後も、試行のたびに全体を読むので、D1 の無料のプランの読み取りの上限（1 日 500 万行）に早く近づく。無料のプランでは止まるだけで課金されないので、受け入れる。
- 共有のデモでは、写真を追加・削除させない（API でも断る）。デモの ID が漏れても、R2 に書き込ませないためである。
  デモの写真は、seed（docs/spec.md の「デモ用のデータ」）が wrangler で D1 と R2 に直接入れる。上限を判定する API を通らないが、入れるのはリポジトリの `seed/photos/` の写真だけで（シンボリックリンクを通る写真とハードリンクの写真は断り、外のファイルを読まない）、seed が入れる前に、1 枚の大きさ・1 レシピの枚数・ワークスペースの合計・アプリ全体の合計の上限を確かめる。
  seed は毎日 `seed-demo.yml` で動き、写真のデータを消して入れ直すので、R2 の書き込みの操作が 1 日に写真の枚数（と、R2 に書けるかを確かめる 1 回）だけ増える（月に数千回で、無料の範囲より十分に小さい）。
- ワークスペースを消すと、アプリ全体のワークスペースの数と写真の合計の枠が空く。作る数（UTC の 1 日に 20 個）と写真の追加の回数（1 日に 200 回）は、消しても残る記録（`workspace_creations`・`photo_uploads`）で数えるので戻らない。
  作ると消すを繰り返しても、1 日に作れる数は増えない。
- 共有のデモのワークスペースは消させない（API でも `403`）。画面の「ワークスペースを削除する」は、Cookie の自分のワークスペースだけを消し、見ているデモは消さない。

サービスごとに、使いすぎたときの動きと、量を抑える仕組みは次のとおり（料金と無料の範囲は 2026-11 時点の公式の文書による）。

| サービス | 使いすぎたとき | 量を抑える仕組み |
| --- | --- | --- |
| Workers | 無料のプランでは 1 日 10 万リクエストを超えると止まる（Error 1027）。有料のプランでは課金される | IP アドレスごとの回数の制限 |
| D1 | 無料のプランでは、読み書きの量と保存量の上限で止まる。有料のプランでは課金される | アプリ全体のワークスペースの数・ワークスペースごとのレシピの数・項目の長さ・ページ分け・最終利用日時の書き換えを 1 時間に 1 回に |
| R2（写真） | 無料の範囲（保存 10 GB-月、書き込みの操作 100 万回/月、読み取りの操作 1,000 万回/月）を超えると**課金される** | アプリ全体の写真の合計の大きさと、1 日の追加の回数の上限を、R2 に書き込む前に D1 で判定する。ワークスペースごとの合計とレシピごとの枚数の上限 |

入れなかったもの:

- Cloudflare Turnstile（ボットの判定）: アプリ全体の上限で費用は守れる。画面と seed（API）の両方からの作成との両立が要り、外部のスクリプトを画面に読み込むことにもなる。
- `wrangler.toml` の `[limits]`（1 リクエストあたりの CPU 時間）: 無料のプランでは 1 回 10 ms に決まっている。
- WAF のレート制限のルール: WAF は自分のドメイン（ゾーン）に付ける設定で、`workers.dev` の URL には使わない前提にしている。

利用者の作業（ダッシュボードで行う）:

- 課金されうるサービスを使う前に、予算の通知（Budget alerts）を設定する。Manage Account > Billing > Billable Usage で Create budget alert を選び、金額を決める。
  通知は前日までの利用で 1 日 1 回判定されるので、すぐには届かない。通知は利用を止めない。
- 有料のプランでは、Workers の利用額の上限（spending limits）を設定できるかも確かめる。R2 には、利用を止める上限の設定が無い。

## サプライチェーン攻撃の対策

- 公開から 7 日たっていない版は使わない。悪意のある版の多くは、公開から数日のうちに見つかって取り下げられるためである。
  - Dependabot: `cooldown` で 7 日待つ。脆弱性を直す security update は待たずに届く。
  - mise: `minimum_release_age = "7d"`
  - pnpm: `minimumReleaseAge: 10080`（単位は分）
  - Cargo: `registry.global-min-publish-age = "7 days"`（Rust 1.100 から。Rust を 1.100 に上げるときに設定する）
- 依存はすべて lockfile で固定する（`Cargo.lock`・`pnpm-lock.yaml`・`mise.lock`）。CI は lockfile と食い違うと失敗する。
  mise が `cargo install` で入れる worker-build は、配布元の `Cargo.lock` に従って `--locked` でビルドされる。ただし `cargo install` は Cargo の待ち日数の設定を使わないので、worker-build の版は公開から 7 日たったものを手で選ぶ。
- GitHub Actions は workflow lockfile（`.github/workflows/actions.lock`）で、使う action とその action が使う action を commit に固定する。
- pnpm は、許可したパッケージのインストール時のスクリプトだけを実行する。
