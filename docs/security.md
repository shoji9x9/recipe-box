# セキュリティ

- コミットと CI で、gitleaks が秘密情報の混入を調べる。GitHub の secret scanning と push protection も有効にしている。
- 依存の更新と脆弱性の通知は Dependabot が担う。Rust の依存は cargo-deny でも調べる。
- workflow は、job ごとに最小の権限だけを与え、actionlint・ghalint・zizmor・CodeQL で調べる。
- 脆弱性の報告の仕方は [SECURITY.md](../SECURITY.md) にある。

## 費用の対策

ログインの無い公開アプリなので、誰でも API を呼べる。自動化した攻撃で、ワークスペースと IP アドレスを使い分けながらデータを作られても、費用が決まった上限を超えないようにする。

上限は 3 つの層で設ける。下の層ほど、攻撃者が回避できない。

| 層 | 上限 | 超えたとき | 回避の手段 |
| --- | --- | --- | --- |
| IP アドレスごと（Rate Limiting、おおよそ） | ワークスペースを作る: 60 秒に 10 回。書き込む API（レシピの登録・更新・削除、写真の追加・削除、ワークスペースの削除）と画面の書き込み: 60 秒に 30 回 | `429` | IP アドレスを変える |
| ワークスペースごと | レシピ: 80 件。本文: 128 KiB。料理名 100・材料 2,000・手順 5,000 文字。写真: 1 枚 4,000,000 バイト・1 レシピ 5 枚・合計 50,000,000 バイト | `409`・`413`・`400` | ワークスペースを作り直す |
| **アプリ全体**（D1 で数えて厳密に判定） | ワークスペース: 100 個。作る数: UTC の 1 日に 20 個。写真: 追加 UTC の 1 日に 200 回（写真の合計 5,000,000,000 バイトは、ワークスペースの数とワークスペースごとの合計の上限で守る） | `503` | **回避できない** |

- 画面で写真をまとめて選んでも、JavaScript が 1 枚ずつ、写真のバイト列そのものとして送る（docs/spec.md の「画面」）。
  - IP アドレスごとの書き込みの回数の制限は、送った写真 1 枚ごとに 1 回、その小さな版（docs/spec.md の「写真」の「小さな版」）を送れば、もう 1 回数える。1 回の操作で送るのはレシピの残りの枚数（5 枚、小さな版と合わせて 10 回）までで、表の制限より十分に小さい。
    ただし、形式の誤りなどで断られた写真は残りの枚数を減らさないので、送り直しを続ければ、ほかの書き込みと同じく制限に当たる。
  - 1 日の追加の回数は、まとめて選んだときも、写真の行を D1 に入れられた写真だけを数える。いつ行を入れるか（本文を読み終える前か後か）と、後で行を消しても数えた回数が戻らないことは、API と同じで、docs/spec.md の「写真」に書いた。
  - 途中で `429`・`503` などが返ったら、残りの写真は送らない。
  - 上限の判定はすべてサーバーで行う。画面の JavaScript の確かめ（送る枚数・大きさ・空のファイル）は、送る手間を省くためだけである。
- レシピは 1 件で最大およそ 29 KB（7,200 文字をすべて 4 バイトの文字で書いた場合）なので、D1 に入るレシピは最大でも 100 × 80 × 29 KB ≒ 230 MB で、1 つの D1 の上限（無料のプランで 500 MB）の半分に収まる。
  ワークスペースの数の上限（100 個）は、実際に使われると見込む数（50 個ほど）の 2 倍にしている。レシピの数の上限（80 件）は、デモに 1 ページ 20 件で 3 ページ以上のサンプルを入れられる数にしている。
- アプリ全体の上限に達すると、攻撃者だけでなく全員が新しくワークスペースを作れなくなる。費用が際限なく増えるより良いとし、受け入れる。使われなくなったワークスペースは 14 日で自動で消える（docs/spec.md）ので、そのあとはまた作れる。
- 写真（R2）は、無料の範囲を超えると課金されるので、R2 に書き込む前に D1 で上限を判定する。
  - 保存量: アプリ全体の写真の合計は、ワークスペースの数の上限（100 個）× ワークスペースごとの合計の上限（50,000,000 バイト）= 5,000,000,000 バイト（5 GB）までで、無料の範囲（10 GB-月）の半分である（下の「写真を追加するとき」）。
  - 書き込みの操作（Class A）: 写真の追加は 1 日 200 回なので、月に最大 6,200 回で、無料の範囲（100 万回/月）より十分に小さい。
    小さな版（docs/spec.md の「写真」の「小さな版」）は、1 枚の写真に 1 つまでなので、書き込みは多くとも写真の追加と同じ数だけ増える（月に最大 12,400 回）。
    小さな版を作る前からある写真にも 1 つずつ足せるが、その数はワークスペースの写真の数（1 つのワークスペースで 400 枚まで）で決まる。
    写真を消しても回数は戻らない（`photo_uploads` に記録を残す）ので、追加と削除を繰り返しても増えない。一覧（ListObjects、Class A）は使わない。1 つずつの削除（DeleteObject）は無料である。アプリが使うまとめての削除（DeleteObjects）は、公式の料金の一覧に載っておらず、無料かを確かめられていない。
    そのため、どの行からもたどれないデータ（レシピやワークスペースを消した後の R2 の削除が失敗したときなど）は、一覧で探して片付けない。
    残っても費用は保存量だけで、起きるのは R2 の削除が失敗したときに限られる（小さな版を書いている間に写真が消され、その後の小さな版の R2 の削除が失敗したときも同じ）。D1 の行だけが残る逆の形は、自動削除が片付ける（docs/spec.md の「写真」）。
  - 読み取りの操作（Class B）: 写真のデータの読み取り 1 回が、Worker のリクエスト 1 回になる。一覧も、写真のあるレシピの先頭の写真を、1 ページに最大 20 枚読む（写真のある最初のカードの写真のほかは、見える所に来てから読む）。無料のプランの Worker は 1 日 10 万リクエストで止まるので、月に最大 310 万回で、無料の範囲（1,000 万回/月）に収まる。
    写真には `Cache-Control: private, max-age=86400` を付け、同じ写真を同じブラウザで 1 日は読み直させない。有料のプランでは Worker が止まらないので、この見積もりは成り立たない。
  - 写真を追加するときに D1 で数えるのは、レシピの枚数・1 日の回数・ワークスペースの合計で、どれも索引で読み、`photos` の全体は読まない。
    アプリ全体の合計は数えない。数えると、追加のたびに `photos` の全体を読むことになり、D1 の読み取りが写真の数とともに増えるためである。
    代わりに、ワークスペースの数とワークスペースごとの合計の上限で守る。次のことから、アプリ全体の合計は 5 GB を超えない。
    - 写真の行は、レシピを通してワークスペースにつながる（外部キー）ので、アプリ全体の合計は、ワークスペースごとの合計の和である。
    - ワークスペースの数は、作る文の中で D1 で数える（共有のデモも、印の付いたワークスペースも数える）。
    - ワークスペースごとの合計は、書き込みや削除が終わっていない印の付いた行も数える。小さな版の大きさも、書いている途中のものを含めて数える。デモの写真は seed が同じ上限で確かめる（下）。
    - どの行からもたどれない R2 のデータ（上の「書き込みの操作」）は数えない。
- 共有のデモでは、写真を追加・削除させない（API でも断る）。デモの ID が漏れても、R2 に書き込ませないためである。
  デモの写真は、seed（docs/spec.md の「デモ用のデータ」）が wrangler で D1 と R2 に直接入れる。上限を判定する API を通らないが、入れるのはリポジトリの `seed/photos/` の写真だけで（`seed/recipes.json` と写真は、シンボリックリンクを通るものとハードリンクを断り、外のファイルを読まない）、seed が入れる前に、1 枚の大きさ・1 レシピの枚数・ワークスペースの合計の上限を確かめる。
  seed は毎日 `seed-demo.yml` で動き、写真のデータを消して入れ直すので、R2 の書き込みの操作が 1 日に写真の枚数（と、R2 に書けるかを確かめる 1 回）だけ増える（月に数千回で、無料の範囲より十分に小さい）。
- ワークスペースを消すと、アプリ全体のワークスペースの数と写真の合計の枠が空く。作る数（UTC の 1 日に 20 個）と写真の追加の回数（1 日に 200 回）は、消しても残る記録（`workspace_creations`・`photo_uploads`）で数えるので戻らない。
  作ると消すを繰り返しても、1 日に作れる数は増えない。
- 共有のデモのワークスペースは消させない（API でも `403`）。画面の「ワークスペースを削除する」は、Cookie の自分のワークスペースだけを消し、見ているデモは消さない。

サービスごとに、使いすぎたときの動きと、量を抑える仕組みは次のとおり（料金と無料の範囲は 2026-11 時点の公式の文書による）。

| サービス | 使いすぎたとき | 量を抑える仕組み |
| --- | --- | --- |
| Workers | 無料のプランでは 1 日 10 万リクエストを超えると止まる（Error 1027）。有料のプランでは課金される | IP アドレスごとの回数の制限 |
| D1 | 無料のプランでは、読み書きの量と保存量の上限で止まる。有料のプランでは課金される | アプリ全体のワークスペースの数・ワークスペースごとのレシピの数・項目の長さ・ページ分け・最終利用日時の書き換えを 1 時間に 1 回に |
| R2（写真） | 無料の範囲（保存 10 GB-月、書き込みの操作 100 万回/月、読み取りの操作 1,000 万回/月）を超えると**課金される** | 1 日の追加の回数・ワークスペースごとの合計・レシピごとの枚数の上限を、R2 に書き込む前に D1 で判定する。アプリ全体の合計は、ワークスペースの数とワークスペースごとの合計の上限で守る |
| 静的アセット（CSS・htmx） | 無料で、回数の上限も無い。Worker を起動しないので、Workers のリクエストに数えない | 要らない |
| Cron Triggers（自動削除） | 別の料金は無く、Workers のリクエストと CPU 時間に数える | 1 時間ごと（1 日 24 回）だけ動く（`wrangler.toml` の `[triggers]`）。1 回の実行で処理する数を絞り、D1 と R2 の呼び出しを、無料のプランの 1 回の実行の上限（50）に収まる 44 回までにする（docs/spec.md の「ワークスペースによるデータの分離」） |
| Rate Limiting の binding | 公式の料金の一覧に記載が無い | 要らない |
| Workers のログ | 無料のプランでは、量の上限に達すると取り込まれなくなるだけで、課金されない。有料のプランでは、含まれる量を超えると課金される（下の「ログ」） | 出すのはエラーと、定期の自動削除が終わった知らせ（1 時間に 1 行）だけで、リクエストごとの記録（invocation logs）は残さない |

表のサービスは、R2 と、料金の記載が無い Rate Limiting の binding を除き、無料のプランでは費用が増えないか、無料の範囲で止まる。
R2 は Cloudflare が止めないので、アプリの上限で無料の範囲に収める（上の「写真（R2）」）。
GitHub Actions（`deploy.yml`・`seed-demo.yml` など）は、公開リポジトリなので無料である。Cloudflare の側の操作は、seed が上の見積もり（月に数千回）で、`deploy.yml` は main に入るたびに数回なので、無料の範囲より十分に小さい。

有料のプランに変えた場合の目安（無料の枠を超えた分）:

- 普通のリクエストは、100 万回あたり約 $0.4〜0.9 である（Workers のリクエストと CPU 時間に、写真を読むときは R2 の読み取りの操作（Class B）が加わる。CPU 時間は 1 回 5〜10 ms とした）。

入れなかったもの:

- Cloudflare Turnstile（ボットの判定）: アプリ全体の上限で費用は守れる。画面と seed（API）の両方からの作成との両立が要り、外部のスクリプトを画面に読み込むことにもなる。
- `wrangler.toml` の `[limits]`（1 リクエストあたりの CPU 時間）: 無料のプランでは 1 回 10 ms に決まっている。
- WAF のレート制限のルール: WAF は自分のドメイン（ゾーン）に付ける設定で、`workers.dev` の URL には使わない前提にしている。

利用者の作業（ダッシュボードで行う）:

- 課金されうるサービスを使う前に、予算の通知（Budget alerts）を設定する。Manage Account > Billing > Billable Usage で Create budget alert を選び、金額を決める。
  通知は前日までの利用で 1 日 1 回判定されるので、すぐには届かない。通知は利用を止めない。
- 有料のプランでは、Workers の利用額の上限（spending limit）を設定でき、達すると新しい呼び出し（リクエストと Cron Trigger）を止められる。
  ただし数えるのは Workers のリクエストと CPU 時間の料金だけで、D1・R2・ログの料金は含まない（[公式の文書](https://developers.cloudflare.com/workers/platform/spend-management/)）。R2 には、利用を止める上限の設定が無い。

## 写真のメタデータ

写真の EXIF などには、撮った場所（GPS の位置）が入ることがある。写真はワークスペースの ID を知る人に見えるので、保存する前に取り除く（どの経路の追加でも同じ。仕組みは docs/spec.md の「写真」）。
Worker の CPU 時間を抑えるため、ファイルの頭の部分（画像のデータより前）だけを書き換え、画像を展開しない。そのため、次のものは残りうる。

- JPEG の、最初の画像の後ろ（EOI の後）にある 2 枚目の画像（スマートフォンの HDR のゲインマップや、MPF の画像など）と、それに付いた EXIF。
- JPEG の、最初の画像のデータ（SOS）より後ろに置かれた APP セグメント（ふつうの写真には無い）。
- PNG の、画像のデータ（IDAT）より後ろの文字のチャンク（`tEXt`・`zTXt`・`iTXt`）と `eXIf`。`eXIf` は仕様で IDAT より前に置くので、ふつうは消える。
- WebP の、`VP8X` の印と食い違って置かれたメタデータ（印でメタデータを持つと分かる WebP と、拡張の無い形（`VP8 `・`VP8L`）の後ろにチャンクを付け足した WebP は断る）。

画面の写真を追加する欄の近くに、残ることがあると書く。共有のデモの写真（`seed/photos/`）には、位置情報が無いことを確かめてある。

写真の小さな版（docs/spec.md の「写真」の「小さな版」）は、メモリーに読んだ小さなファイル（500,000 バイトまで）なので、頭の部分だけでなく全体を見て、メタデータを持ちうるセグメント（APP1 の Exif・XMP、ほかの APPn、COM）と画像の終わりより後ろを 0 で埋める。
そのため、上に挙げた頭より後ろの穴は無い。ただし、画像を展開するのに要るものとして残す APP0 の JFIF・JFXX（JFXX は小さな画像を持てる）、APP2 の ICC プロファイル、APP14 の Adobe の中身は見ない。
画面の JavaScript が canvas で作る小さな版には、撮った場所は入らない。

## ログ

- Workers のログ（`wrangler.toml` の `[observability]`）を有効にし、アプリが `console` に出したもの（エラーなど）を、後から Cloudflare のダッシュボードで見られるようにする。
  - 2026-11-30 までは、無料のプランでは 1 日 200,000 件まで、3 日残る。有料のプランでは月 2,000 万件まで含み（超えた分は 100 万件あたり $0.60）、7 日残る。
  - 2026-12-01 からは、Cloudflare Observability の料金に変わる。無料のプランでは取り込みが 1 日 0.5 GB までで、7 日残る。上限に達すると、その日は UTC の 0 時まで取り込まれず、課金されない。
    有料のプランでは、取り込みは月 50 GB まで含み（超えた分は 1 GB あたり $0.25）、保存は 10 GB-月まで含む（超えた分は 1 GB-月あたり $0.10）。
  - 公式の文書: [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)・[Observability の料金](https://developers.cloudflare.com/observability/pricing/)・[Workers の料金](https://developers.cloudflare.com/workers/platform/pricing/)
- ワークスペースの ID は、知ればそのワークスペースを読み書きできる鍵なので、ログに残さない。
  - アプリがログを出すときは、エラーもそうでない知らせも、ID を伏せてから出す（`src/error.rs` の `log_error` と `log_info`。アプリが自分で出すログは、この 2 つだけから出す）。
    panic の文は `console_error_panic_hook` がそのまま `console.error` に出し、伏せない。panic の文に ID を入れない（`unwrap`・`expect` の文に ID を書かない）。
  - リクエストごとの記録（invocation logs）は残さない（`invocation_logs = false`）。Cloudflare は Cookie などのヘッダーを伏せるとしているが、API の `X-Workspace-Id` が伏せられるかを確かめられないためである。
    リクエストごとの CPU 時間などは、`wrangler tail` で見る（そのときだけ流れ、残らない）。
  - invocation logs を残さなくても、アプリが出したログの行には、Workers Logs がそのリクエストのメソッド・パス・URL（クエリを含む）を付ける。リクエストのヘッダー・Cookie・本文は付けない。
    2026-11-17 に、同じ設定（`invocation_logs = false`）の使い捨ての Worker に、偽の値の `X-Workspace-Id`・Cookie・フォームの本文を付けて送り、`fetch` の中ですぐに出した `console.error` の行で確かめた。
    応答を返した後（`waitUntil` など）に出した行に、同じものが付くかは確かめていない。
  - そのため、URL にワークスペースの ID を入れない（ID は、ヘッダー・Cookie・フォームの本文でだけ送る）。
    アプリが作る URL に入るのは、レシピと写真の ID（ワークスペースの ID が無いと使えない）・ページの番号・検索の語（`q`）・小さな版の幅（`width`）で、エラーの行と一緒に残る。
    URL は `log_error` の伏せる処理を通らないので、利用者が検索の欄に ID を貼ったときや、クライアントが勝手なパスやクエリを送ったときは、その文字がそのまま残る。
- 定期の自動削除の結果（D1 の `cleanup_runs`）を確かめる job（`seed-demo.yml` の `check-cleanup`）は、公開リポジトリの Actions のログに出る。
  そのため、成功か失敗かと、最後の成功から経った時間と、残っているものの種類だけを出し、数・ID・アカウントの状況は出さない（`scripts/check-cleanup.ts`）。
  D1 のデータベースの ID は、seed の job と同じく `::add-mask::` で伏せる。`cleanup_runs` は、ワークスペースの ID を持たない。

## サプライチェーン攻撃の対策

- 公開から 7 日たっていない版は使わない。悪意のある版の多くは、公開から数日のうちに見つかって取り下げられるためである。
  - Dependabot: `cooldown` で 7 日待つ。脆弱性を直す security update は待たずに届く。
  - mise: `minimum_release_age = "7d"`
  - pnpm: `minimumReleaseAge: 10080`（単位は分）
  - Cargo: `.cargo/config.toml` の `registry.global-min-publish-age = "7 days"`（Rust 1.100 から）。依存を足すときと `cargo update` のときに、これより新しい版を選ばない。
    `cargo update --precise` で版を指定しても断るので、脆弱性を直す版でも 7 日待つ。Dependabot の security update が、この設定のために作れないこともある。
    急ぎで要るときは、理由を PR に書いたうえで、その 1 回だけ `CARGO_RESOLVER_INCOMPATIBLE_PUBLISH_AGE=allow cargo update -p <クレート> --precise <版>` で入れる（設定は消さない）。
- 依存はすべて lockfile で固定する（`Cargo.lock`・`pnpm-lock.yaml`・`mise.lock`）。CI は lockfile と食い違うと失敗する。
  mise が `cargo install` で入れる worker-build は、配布元の `Cargo.lock` に従って `--locked` でビルドされる。ただし `cargo install` は Cargo の待ち日数の設定を使わないので、worker-build の版は公開から 7 日たったものを手で選ぶ。
- GitHub Actions は workflow lockfile（`.github/workflows/actions.lock`）で、使う action とその action が使う action を commit に固定する。
- pnpm は、許可したパッケージのインストール時のスクリプトだけを実行する。
